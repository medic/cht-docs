## Highlights

5.3.2 is a patch release with two fixes for Nouveau, the CouchDB search service that drives user replication and server-side purging. It also fixes a 5.3.0 regression in how reports display their subject.

### CouchDB 3.5.3

The CHT upgrades CouchDB to 3.5.3. This version fixes upstream bugs ([apache/couchdb#6118](https://github.com/apache/couchdb/issues/6118)) that caused Nouveau index rebuilds to fail after documents were purged from the database, for example with the [archiving endpoint](/technical-overview/data/performance/archiving/). Without that index, users can't sync ([#11456](https://github.com/medic/cht-core/issues/11456)).

### Smaller Nouveau queries

API and Sentinel request at most {{< format-number 20_000 >}} results per page from the `docs_by_replication_key` Nouveau index, down from {{< format-number 200_000 >}}. CouchDB sends the limit to every shard, so the old value could exhaust the Nouveau heap during server-side purging and leave the index unusable until Nouveau restarted. Replication authorization pages through larger result sets instead of requesting them all at once ([#11490](https://github.com/medic/cht-core/issues/11490)).

### Report subjects with an empty `patient_id`

When an offline user creates a person and then submits a report about them before syncing, the person has no shortcode yet, so the report saves an empty `fields.patient_id`. Since 5.3.0, the reports list and report detail showed these reports' subject as plain text with no link to the contact, and showed the submitter's lineage instead of the subject's. The CHT falls back to `fields.patient_uuid` when `fields.patient_id` is empty, so these reports display their subject correctly ([#11500](https://github.com/medic/cht-core/issues/11500)).

## Upgrade notes

### Instances with a broken Nouveau index

If your Nouveau indexes work, upgrade to 5.3.2 as usual. This includes instances that archived documents but haven't rebuilt an index since.

If an index rebuild already failed on your instance and users can't sync, upgrading to 5.3.2 alone doesn't repair the index:

- Upgrading from the **Upgrade** page in the Admin app, or with the upgrade API, fails because the upgrade queries the broken index.
- Upgrading with `helm upgrade`, or by changing the image versions in your Docker Compose files, succeeds but doesn't rebuild the index. 5.3.2 doesn't change the index definitions, so nothing triggers a rebuild.

To fix the index, run the the [repair script](https://gist.github.com/jkuester/6ab703b2d12265d2b181bc020b73571b) on the 5.3.0 or 5.3.1 instance, then upgrade. The script requires the default 5.3.0 or 5.3.1 index definitions. 

If an earlier upgrade attempt left a broken staged index, the upgrade replaces your working index with it. Before upgrading, stage the upgrade again or delete the staged index.

To upgrade from 5.3.0 or 5.3.1 to a later release that changes the `docs_by_replication_key` index, upgrade to 5.3.2 first.
